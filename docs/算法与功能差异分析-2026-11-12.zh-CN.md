# Spektramat 与 spektrafilm / SpektraLab 差异分析

## 结论先行

截至 2026-11-12，Spektramat `e7baa584bf631d64e23e7acc639f81cacbc673ed` 是把 spektrafilm 的“场景光 → 胶片 → 印相/扫描”物理模型移植到 Android 的产品化实现，同时加入了手机拍摄、胶片录像、Sony USB 监看、片库、片边/日期和移动端整饰。它不是 spektrafilm Python 参考实现的逐像素等价版本：全尺寸成片固定使用 41³ 印放/扫描 LUT，实时预览和取景又省略了若干需要邻域计算的效果。

相对最新 SpektraLab 2.3.2 Mac Catalyst（`1952c63537ec576d24422f1065b12495631346a5`），两者的物理管线相近，但产品取舍相反：Spektramat 的优势是 Android 相机和 Sony USB 现场工作流；SpektraLab 的优势是完整色彩管理、场景曲线/HDR、几何编辑、图库/会话与专业导出。下面的“SpektraLab”默认指当前 `app/SpektraLab` Mac 产品；仓库中的 `desktop/`、`windows_UI/` 是另一个功能覆盖不齐的端口，不并入主矩阵。

## 算法差异：Spektramat 相对 spektrafilm

### 共同的管线骨架

两者都按“场景预处理/测光 → RGB 到胶片曝光 → 胶片显影（曲线、DIR、颗粒）→ 印相或直接扫描 → 扫描颜色变换”的顺序工作。Spektramat 的 `spektra_engine.hpp:1-23` 明确按 spektrafilm runtime 分阶段移植；`spektra_engine.cpp:733-777` 实现散射和三次 halation，`:780-844` 实现 DIR 空间扩散，`:847-930` 实现分层颗粒，`:940-1026` 实现印相、眩光、CAM16 和锐化。

### 逐阶段差异

| 阶段 | 最新 spektrafilm | Spektramat 当前实现 | 影响 |
|---|---|---|---|
| 输入色彩与 RGB→胶片 | `params_schema.py:169-193` 默认输入 ProPhoto RGB，可选输入/输出色域压缩；`filming.py` 支持 Hanatos 2025 或 Mallett 2019 | 输入固定为 scene-linear sRGB，JNI 输出 RGBA8 sRGB；只实现 Hanatos 2025。胶片 tc 表由完整引擎生成后再供 GPU 使用 | ProPhoto/AdobeRGB/P3 等宽色域素材不会保留 spektrafilm 同样的输入语义；极端颜色和高光压缩也不等价 |
| 自动曝光 | `params_schema.py:49-57` 默认 `center_weighted`，每次运行按图像测量，可选多种方法 | 导入时做一次中心加权测光并保存 `meteredEv`；`lt_jni.cpp:648-652` 把 full engine 的 auto exposure 关闭，grade 阶段直接使用已保存读数和用户 EV | 同一原片改变画面或测光策略时，Android 的曝光状态是“导入时快照”；不等于 Python 每次运行重新测量 |
| 胶片曝光中的光学效果 | 可独立调 diffusion filter、lens blur、UV/IR filter、highlight boost、halation 细节 | full 引擎保留散射与 halation，但常量固定（`spektra_engine.cpp:28-58`），UI 主要控制总量；没有 spektrafilm 的全部相机滤镜/模糊参数 | 可调物理自由度减少，特定镜头/滤镜/高光行为不能复现 |
| 胶片显影与 DIR | 曲线、层间矩阵和空间扩散参数均来自 runtime 参数 | full 引擎保留矩阵和空间扩散（`spektra_engine.cpp:780-844`），但 Android 控件只暴露总强度；固定 `20/200 µm` 扩散参数 | 默认观感接近，参数扫描/科研复现能力较弱 |
| 颗粒 | spektrafilm 的 Poisson/binomial 粒子、三子层、染料云和微结构 | full 引擎保留分层粒子和微结构；增加 `grain_amount` 混合（`spektra_engine.cpp:847-930`），随机数序列不承诺与 Python 相同 | 统计特征可接近，但不能把像素级颗粒当作同一随机实现 |
| 放大机 | `printing.py:39-116` 默认直接光谱积分；可选 LUT、预闪、放大机 diffusion 和 print curve morph；默认 `print_exposure_compensation=True`、normalize=True | `spektra_engine.cpp:494-534` 使用固定 TH-KG3、数据库中性滤色和 41³ enlarger LUT；`RenderParams` 默认 print compensation=false | 印放密度由 41³ 三线性表近似；相机曝光补偿会移动最终成片亮度，而不是按 Python 默认抵消 |
| 相纸显影 | 可使用 `density_curves_morph` 改变相纸曲线 | 使用资源中固定/烘焙的相纸曲线；没有独立 morph 控件 | 无法复现参考实现的相纸曲线连续变形 |
| 扫描与输出 | `scanning.py:46-128` 可选扫描 LUT，支持 lens blur、黑白点修正、锐化和输出色域压缩；输出色彩空间可选 | `spektra_engine.cpp:958-1026` 走 41³ scanner LUT，固定 CAM16-UCS 与 0.7/0.7 unsharp 参数，最终 sRGB 8-bit | 显示结果受固定输出色域和 LUT 分辨率限制；不等于直接 81 波长积分的 Python 路径 |
| 负片直扫 | `scan_film` 是显式 pipeline 分支；SpektraLab 还提供 DI 卡/中性负片流程 | `Look.scanFilm`（`Look.kt:63-65`）直接跳过印相，把底片送入 scanner | Android 的“直接扫描底片”不应描述成 SpektraLab 的 Cineon/neutral DI |

### Full 成片、预览、相机和监视器不是同一条路径

1. **全尺寸成片**：RAW/平台解码 → scene grade → C++ full filming/develop/printing/scanning → finishing → JPEG95。`lt_jni.cpp:615-707` 在 full develop 时关闭引擎自动曝光、映射 UI 参数，并在 `rgb_out_linear` 后执行 finishing。
2. **暗房 GPU 预览/普通缩略图**：`latent.glsl` 与 `lt_fast.cpp` 共用文本。它使用 film/print/scan 表做逐像素运算，但明确省略 scatter、DIR 空间扩散、glare 和 scanner sharpening（`latent.glsl:1-28`）。颗粒用均值/方差表加 PCG 高斯噪声近似（`:154-187`），不是 full 引擎逐颗粒 realization。
3. **暗房片边/日期**：片边和日期需要引擎把画布扩大并把标记曝光到底片上；`DarkroomState.kt:35-44` 因此改走小尺寸 proof，而不是 GPU 直接画。`FilmPreview.kt:207-253` 预览光晕把 full 的三次反射合成半径 `1.25r` 的单高斯，并在长边 512 的小浮点缓冲中模糊；不支持浮点目标的 GPU 会隐藏预览光晕，但成片仍有。
4. **手机相机/录像**：`Programs.kt:282-300` 把 display-referred sRGB 取景流线性化后套 grade/film/print/finish；没有 halation 多 pass。视频录制由 `CameraRig.kt:289-300` 走 1080p/720p/480p 质量档。
5. **Sony 监视器**：`Monitor.kt:378-398` 走 `renderFast`，注释明确为“no grain and no halation”；它优先保证 USB 取景速度，与 full 成片的颗粒/光晕不相同。

因此，“预览看起来和最终成片完全一样”不是当前实现保证；现有测试只证明受控条件下 fast CPU twin 与 Spektramat 自己的 full engine 接近。

## 这些差异对实际结果的含义

- **看起来相近不代表数值相同**：只要输入超过 sRGB、开启大范围高光/阴影、改变颗粒空间尺度，或比较预览与全尺寸成片，LUT 分辨率、固定参数和邻域效果省略都会产生差异。
- **Android 的曝光语义是移动工作流语义**：原片导入时测光一次；JNI full path 用 grade 中的曝光，不再二次自动测光。spektrafilm reference 默认按当前运行图像测光。SpektraLab Mac 新帧默认使用 `balanced` 产品测光，但其 C++ 引擎默认字段仍是 `center_weighted`，旧编辑/未传该字段会保留兼容语义（`FilmParams.swift:480-495`、`params.hpp:339`、`engine.cpp:178-203`）。
- **Mac 的 print compensation 也要分产品默认与 reference 默认**：spektrafilm schema 默认 true；SpektraLab 产品在 `engine.cpp:170-203` 明确设置 false；Spektramat `RenderParams` 默认 false（`spektra_engine.hpp:46-99`）。因此 Android 与当前 Mac 的这个产品默认一致，但与 Python reference 不一致。
- **RAW 路径不同**：Spektramat 的 LibRaw 路径输出 linear sRGB，并处理 DNG 白平衡/镜头暗角映射；spektrafilm 的参考工具链以 rawpy/ACES 和可选 Lensfun 为主；SpektraLab Mac 以 ProPhoto 工作空间和 RAW Kelvin WB 为产品语义。不要用同一个 RAW 文件的最终 RGB 直接推断三者算法差异，必须先固定解码、色彩空间和曝光。

## 风险与优先级建议

1. **P0：限制 DIR 耦合范围。** `Look.kt` 当前把层间效应暴露到 200%；建议 UI、JSON 反序列化和 JNI/引擎入口都限制到 1.5，并为旧配方做钳制和迁移提示。增加 1.5、1.736 和 2.0 的回归测试，避免非单调反演产生不可预期颜色。
2. **P1：标明预览与成片的效果边界。** 在光晕、DIR、颗粒控件旁说明暗房 GPU 预览是近似；相机、录像和 Sony 监看不含光晕/邻域扩散；最终效果以全尺寸冲印为准。
3. **P1：固定资产与 parity 的复现链。** 当前 `Spektramat/tools` 只有 host 检查，`bake_assets.py` 和 Python parity 位于 workspace 外层 `tools/`。建议将生成脚本、profile 提交号、输入哈希和命令纳入仓库或发布记录，并在 CI 对最新 spektrafilm 做常规 profile parity。
4. **P2：补齐黑白颗粒校准和输出能力。** 记录黑白 stock 的颗粒模型/标定来源；按用户价值增加 16 位 TIFF、Display P3/Adobe RGB、可恢复批处理队列和更完整扫描/预闪控制。
5. **P3：扩展移动端工作空间。** 评级/色标/变体、自由裁切/透视、通道混合器、数字中间片、HDR/EDR 与半格双图拼接属于产品数据模型扩展，应单独规划。
